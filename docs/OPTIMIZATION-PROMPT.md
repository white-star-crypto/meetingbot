# 合议 / MeetingBot 后续优化提示词

> 用法：把下面整段交给负责下一轮设计与实现的 Agent。它先做用户视角审计和优先级，再改代码；不要一上来堆功能。
>
> **项目工作目录（源码）：** `<项目目录>`
> **便携版目录：** `<便携版目录>`
> **主界面：** `public/panel.html`
> **服务端：** `src/panel-server.mjs`
> **配置：** `meeting.config.local.json`（本地） / `examples/config.example.json`（示例）
>
> 如果你在另一台机器/另一个目录接这活，以**仓库根目录**为准；先 `pwd`，不要照抄上面这台机器的绝对路径。

---

你是 **合议（MeetingBot）** 的产品设计负责人 + 前端体验工程师 + AI 协作产品研究者。

合议是一个本地桌面应用：多个模型先开会（独立提案 → 交叉批判 → Condorcet 投票 → 主 Bot 决策），再把结论用于真实任务；同时带私聊 Agent、工具调用、权限分级、DSH 插件市场、上下文压缩和“审图失败 → 回退主 Bot 重新分发”的修复闭环。项目**以后会开源**。

## 这轮任务

在不破坏现有简约、克制、像人类工具的主题风格的前提下，从**真实用户视角**审计并优化这款应用，让它更好用、更耐看、更可信，也更像一个值得长期使用的开源产品。

不要复刻“花哨 AI 仪表盘”。不要加霓虹渐变、夸张玻璃拟态、满屏卡片、无意义动效、假 Agent 工作动画。保持现有骨架：左侧工作区、顶部标题/状态、中间内容流、底部输入区。

## 硬约束

1. 先读当前代码与真实交互，不要凭截图猜。
2. 不破坏现有真实功能：会议、分工、点将、私聊、插件市场、Agent 工具、权限分级、上下文压缩、审图回退、会话菜单、模型选择/置顶/预设。
3. 不把演示数据、占位文案、假按钮说成已完成。
4. 不引入重型前端框架；优先在现有 HTML/CSS/JS 上做渐进增强。
5. 默认权限仍是“只读”；安全提示、控制文件保护、路径边界不能被 UI 优化绕过。
6. 所有新增设置必须有真实作用，不做“只存 localStorage 不生效”的假选项。
7. 保持 1280×820 桌面窗口和窄屏可用；键盘焦点、对比度、滚动条、空状态要一起检查。

## 一、先做用户视角审计

不要先写代码。先回答：

- 第一次打开的人，5 秒内知不知道“这是干什么的”？
- “合议 / 分工 / 点将 / 私聊 / 插件”五个入口，第一次用的人能不能分清？
- 从“我有一个任务”到“拿到可执行结论”，最短路径是什么？中间有没有多余确认？
- 失败时用户是否知道发生了什么、下一步点哪里？
- 设置项是否太多但难找，或者太少但被迫改代码？
- 哪些地方是“给开发者看的”，哪些才是“给用户用的”？
- 哪些操作不可逆、花钱、动权限、动本机文件？这些地方有没有足够但不啰嗦的提示？

输出一份问题清单，按用户影响排序，不要按代码模块排序。

## 二、视觉与排版目标

关键词：**安静、清楚、可信、耐看、像人做的工具**。

请检查并优化：

- 信息层级：标题、说明、状态、操作按钮的视觉权重是否清楚。
- 留白与密度：卡片内边距、列表行高、分组间距是否统一。
- 字体与字号：中文长文本的可读性；不要用过多字号。
- 颜色：强调色只给关键动作；危险色只给危险操作；不要把状态色当装饰。
- 边框与阴影：现有细边框 + 轻阴影很好，不要加重。
- 空状态、加载态、错误态、成功态：都要有明确文案，不要只显示空白。
- 长文本：决策书、插件介绍、工具输出、上下文摘要不能撑破布局。
- 滚动：模型列表、插件列表、文件预览、设置页滚动条要可见、可操作。
- 深色主题：不能只是反色；检查对比度和选中态。
- 响应式：窄窗口下侧栏、模型面板、插件卡片、工具弹层不能互相遮挡。

如果提出视觉改动，请给出具体 CSS 级别描述：间距、字号、颜色变量、最大宽度、断点，而不是只说“更现代”。

## 三、以用户视角增加的人性化功能

优先做“减少困惑、减少重复劳动、减少误操作”的功能，不做打扰式功能。

建议方向（可取舍，但说明理由）：

- 首次使用引导：只做 3 步以内，能跳过，不强制看长文。
- 空状态行动建议：没有会议/没有私聊/没有插件结果时，给一个明确下一步。
- 最近使用与恢复：上次打开的会话、上次的模型/权限/工作模式；崩溃后能恢复。
- 搜索：会话、模型、插件、设置项都能搜；快捷键可发现。
- 快捷键：新会议、发送、切工作区、打开设置、关闭弹层；不要和输入法冲突。
- 撤销/确认：危险操作给一次确认；可撤销的操作给撤销，不要两个都堆。
- 费用/额度感知：会前预估、会后实际 token；不要制造焦虑，也不要隐藏成本。
- 失败恢复：模型失败时显示“哪个模型、哪一步、可重试/换模型”，不要只报红。
- 无障碍：键盘可达、焦点可见、按钮有可读名称、对比度达标。
- 多语言：开源后至少中英文案结构可扩展，不把中文硬编码进逻辑。
- 隐私：明确哪些内容只在本机、哪些会发给模型；插件和工具调用前说清楚。

人性化不等于加动画。能少点一次、少猜一次、少丢一次数据，就是人性化。

## 四、设置页扩展

把设置做成“用户能找到、能理解、能撤销”的控制台。建议分组：

### 外观
- 主题、强调色、紧凑模式、字号、气泡密度
- 侧栏宽度/折叠
- 动效减弱
- 代码/长文本字体

### 会话与上下文
- 默认工作模式
- 上下文策略：压缩 / 缓存摘要 / 仅当前
- 上下文预算显示
- 会话自动恢复
- 会话归档/清理策略

### 模型与 Agent
- 默认阵容、默认私聊 Agent
- 模型选择器默认展开/折叠
- 置顶模型/预设管理
- Agent 最大工具步数
- 工具调用轨迹默认展开/折叠
- 是否允许 Agent 主动提问

### 权限与安全
- 四级权限（只读/工作区/自审/完全权限）
- 免责协议状态
- 审计日志入口
- 危险操作确认策略
- 浏览器/文件/Python 工具开关（按权限）

### 插件
- 插件目录来源
- 默认“发送给 Agent”的 Agent
- 插件风险提示显示
- 已发送/已分析记录
- 过滤不安全/不兼容插件

### 数据
- 运行目录、导出格式
- 备份/恢复
- 清空缓存/会话/上下文
- 打开数据目录
- 导入/导出设置

每个设置都要有：默认值、作用说明、生效方式（立即/重启）、恢复默认。

## 五、优化现有老功能

逐项审计，不要只加新东西：

1. **会话列表**：重命名、置顶、归档、分叉、移动、删除、批量管理是否真的可用；空列表/归档列表是否清楚。
2. **模型选择器**：搜索、滚动、置顶、预设、推理档位是否顺手；选中态是否明确。
3. **私聊**：模型/推理切换、上下文 chip、工具轨迹、提问弹窗、群修/私修按钮是否形成闭环。
4. **会议**：新会议输入、运行状态、失败重试、决策页、历史记录是否顺畅。
5. **插件市场**：搜索、分类、分页、详情、安装命令复制、发送给 Agent 的预填是否不误发。
6. **审图回退**：审图失败后主 Bot 的分工是否可读；下一轮按钮是否明确；不要恢复文件回滚。
7. **权限**：四档文案是否让用户知道“会问/不会问”；免责协议是否只在高风险模式出现。
8. **性能**：9412 条插件目录、长上下文、长决策书、工具输出是否卡顿；需要时做虚拟列表/分页/懒加载。

## 六、开源产品要求

- 文案说人话，不堆内部术语。
- 不引入来源不明、许可证不明的资产。
- 新增依赖必须说明理由、许可证、体积。
- 结构可被贡献者理解：组件边界、状态来源、错误处理、测试入口。
- 关键路径有测试或可复现验收步骤。
- README / docs 与真实行为一致；未完成的功能标“计划中”，不要写成已完成。
- 默认配置必须安全、可运行、无密钥。
- 不把用户数据、密钥、本机路径写进示例或日志。

## 七、输出格式

先给：

1. **用户视角审计**：最影响体验的 10 个问题，按影响排序。
2. **设计方向**：一句话说明这一轮要变成什么样，以及不做什么。
3. **优先级路线**：P0（必须现在修）/ P1（这轮做）/ P2（后续）。
4. **改动清单**：每项写清：
   - 用户问题
   - 具体改动
   - 涉及页面/文件
   - 验收标准
   - 风险/回退
5. **设置项清单**：名称、默认值、作用、生效方式。
6. **视觉规范**：间距、字号、颜色、圆角、阴影、断点；不要只写形容词。
7. **测试计划**：真实点击路径 + 边界 + 失败态 + 键盘/窄屏。
8. 然后再开始改代码。

## 八、验收底线

- 不破坏现有简约主题。
- 不出现新的 `\n\n`、占位假按钮、死设置。
- 真实会议/私聊/插件/权限/上下文/审图回退至少各走一遍。
- 窄屏 960×620 和 1280×820 都要看。
- 深浅主题都要看。
- 所有新增设置要能实际生效。
- 如果时间不够，宁可少做，也不要把半成品说成完成。

请以“这是要开源给陌生人用的产品”为标准，而不是“给作者自己看的 demo”。
